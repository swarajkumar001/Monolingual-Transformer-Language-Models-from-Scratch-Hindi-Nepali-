\begin{abstract}
\noindent
This report covers Phase 1 of the Language Models and Agents individual
project: dataset collection, cleaning, splitting, and tokenizer
construction for two independent, from-scratch decoder-only Transformer
language models. Model H (higher-resource) is \textbf{Hindi}; Model L
(lower-resource, from the assignment's allowed list) is \textbf{Nepali}.
Every number in this report is read directly from a file produced by the
project's own pipeline code -- Hindi from \texttt{clean\_stats.json} and
\texttt{hindi\_pipeline\_manifest.json}; Nepali from
\texttt{nepali/data/final/corpus\_stats.json} and \texttt{split\_stats.json}
-- or the trained tokenizer model files re-measured directly, never
estimated. Both languages clear the assignment's hard 20\% manual-
collection floor; Hindi reaches 101.2\% of the 500M-token planning target
and Nepali reaches 127.0\%. Hindi and Nepali run on two structurally
different pipelines (Hindi: a single-pass cleaner; Nepali: a stage-based
S00--S14 pipeline with MinHash/LSH dedup and absolute per-lane token
targets), described separately throughout rather than forced into one
shared schema. Nepali is this project's second Model L candidate --
Bhojpuri was the original choice and is kept intact in the repository,
superseded once Nepali's own pipeline finished (Section~\ref{sec:results}).
\end{abstract}

\section{Overview}
% =====================================================================

The assignment requires two independent, from-scratch decoder-only
Transformer language models in two different Indian languages: Model H
from a higher-resource language, Model L from a fixed list of
lower-resource languages (Assamese, Bhojpuri, Bodo, Dogri, Konkani,
Maithili, Manipuri, Mizo, Nepali, Sindhi). Both must be built with fully
separate data, tokenizer, vocabulary, and (from Phase 2) weights -- no
sharing, no multilingual training.

\textbf{Model H is Hindi.} Hindi is one of the highest-resource Indian
languages for NLP: Wikipedia, curated corpora like AI4Bharat's Sangraha,
and web-crawled corpora like Fineweb-2 all have large Hindi partitions.
This makes it realistic to reach the assignment's $\sim$500M-token
planning target almost entirely from public sources, while still
requiring genuine manual collection to clear the 20\% floor.

\textbf{Model L is Nepali.} Nepali has considerably more public data
available than several other allowed languages -- AI4Bharat's Sangraha
and IndicCorpV2 both carry sizeable Nepali partitions -- which let this
corpus not just clear the 20\% manual floor but exceed the 500M-token
planning target outright (127.0\%), while still requiring genuine,
sustained manual collection (mainly news-site scraping) to hit the
pipeline's own 100M-token absolute manual-lane floor.

Both languages are Devanagari-script. Hindi's cleaning/tokenization code
is \texttt{scripts/clean\_lib.py}; Nepali's is its own independent
\texttt{corpuslib} package under \texttt{nepali/scripts/} -- not shared
with Hindi's -- keeping every byte of data, every trained model file, and
every decision fully separate per language.

\subsection*{What counts as ``manual'' under the course ruling}

A source counts as \textbf{manual} only if it required work beyond
pointing a downloader at an existing public dataset: a self-run scrape, a
personally extracted Wikipedia XML dump, OCR from a physical or scanned
source, or similarly hands-on collection. A dataset that is just
\textit{labeled} as Wikipedia-derived on Hugging Face does not count.

ever loosening a cleaning filter to manufacture volume.

\section{Cleaning Pipeline}
\label{sec:cleaning}
% =====================================================================

Hindi and Nepali use two different cleaning implementations, described
separately below.

\subsection{Hindi cleaning pipeline}

\texttt{scripts/clean\_lib.py}, run via \texttt{clean\_hindi.py}. Measured
stage order, confirmed from \texttt{clean\_stats.json}'s own checkpoints:

\begin{center}
raw $\to$ malformed-Unicode removal $\to$ too-short removal $\to$
language-ID filter $\to$ exact/near-duplicate removal $\to$ cleaned
\end{center}

\textbf{Normalization: NFC, not NFKC.} NFKC would strip or alter U+200C
(ZWNJ) and U+200D (ZWJ) -- zero-width joiner/non-joiner characters that
are \textbf{semantically meaningful} in Devanagari, controlling whether a
consonant cluster forms a conjunct ligature or stays visually separate.
NFC preserves them.

\textbf{Latin-token removal, digits kept.} 8{,}016{,}102 residual
Latin-script tokens were stripped. Digits are kept.

\textbf{Language filter.} \texttt{langdetect} has \textbf{no `bho' label}
-- it cannot itself identify Bhojpuri text, and Hindi/Bhojpuri share
vocabulary and script closely enough that mislabeled Bhojpuri leaking
into Hindi's corpus was a real risk during collection (Bhojpuri was this
project's original Model L -- see Section~\ref{sec:results} for why it
was superseded by Nepali; this filter and the correction below predate
that switch and remain part of Hindi's own cleaning history, run
unconditionally regardless of which language is currently Model L).
\texttt{dropped\_language.likely\_bhojpuri} is an active reject filter:
any document where Bhojpuri lexical markers
(\dn{बा}/\dn{बाटे}/\dn{बाड़ें}/\dn{एगो}/\dn{गइल}/\dn{भइल}/\dn{कइल}/etc.,
$\geq$2 hits) outnumber Hindi markers
(\dn{है}/\dn{हैं}/\dn{एक}/\dn{गया}/\dn{हुआ}/\dn{किया}/etc.) is dropped
before reaching \texttt{data/cleaned/}. 1{,}365 documents were dropped by
this filter.

\textbf{Historical cross-language correction (Hindi $\leftrightarrow$
Bhojpuri).} \texttt{scripts/validate\_phase1.py}'s cross-language check,
run while Bhojpuri was still Model L, caught 2 documents whose content
hash was shared between the Hindi and Bhojpuri cleaned corpora --
genuinely Bhojpuri news text that \texttt{ai4bharat/sangraha} had sourced
as \texttt{hin}, an upstream labeling error. Both were removed from
Hindi's cleaned corpus. This is why Hindi's final cleaned count is
\textbf{704{,}101}, not \texttt{clean\_stats.json}'s own recorded
704{,}103. This correction is permanent, independent of which language is
currently Model L.

\textbf{Deduplication.} Exact-hash matching on normalized text
(\texttt{dedup\_key}); on a manual/downloaded tie, the manual copy wins.
Near-duplicate detection beyond exact-hash matching was \textbf{not} run
on Hindi's pipeline -- see Section~\ref{sec:limitations}.

\section{Tokenizers}
% =====================================================================

\subsection{Hindi: SentencePiece Unigram}

Trained on Hindi's own train split only. Unigram treats the segmentation
itself as a latent variable, re-estimating piece probabilities via EM --
argued to suit Hindi's agglutinative-suffixing morphology and Devanagari
conjunct clusters better than BPE's greedy, order-dependent merging. This
is structural, not empirically confirmed for Hindi specifically (see
Section~\ref{sec:limitations}) -- though the Nepali subsection below
reports an actual BPE-vs-Unigram comparison that did run, for the other
language. Unigram's suffix-array stage peaked near 5.9GB on this
project's 16GB machine.

\subsection{Nepali: SentencePiece BPE}

\texttt{nepali/configs/tokenizer.yaml} configures \texttt{model\_type:
bpe} as this pipeline's default, configured independently of Hindi's
Unigram choice. The config includes a genuine safety net:
\texttt{compare\_unigram.enabled: true}, set to also train Unigram and
keep whichever scores better \textit{if} BPE's fertility exceeded 2.10
tokens/word. It never triggered -- BPE's measured fertility
(1.4825--1.6988) stayed well under that threshold.

\texttt{byte\_fallback} is explicitly \textbf{disabled}
(\texttt{byte\_fallback: false}), unlike Hindi's \texttt{byte\_fallback=
True} -- a real methodological difference for interpreting UNK rate
below.

\subsection{Why UNK rate is meaningless for Hindi but real for Nepali}

For \textbf{Hindi}, UNK rate reads exactly 0.0 at every vocab size, but
this is structural: \texttt{byte\_fallback=True} means any character
sequence the model cannot represent normally falls back to raw-byte
pieces instead of \texttt{<unk>}. The metric that actually tracks real
out-of-vocabulary pressure for Hindi is \textbf{byte-fallback rate}
(1.83\%--2.02\% across the sweep).

For \textbf{Nepali}, \texttt{byte\_fallback} is disabled, so a 0.0 UNK
rate at every vocab size is not masked by a fallback mechanism -- it
means the trained vocabulary genuinely represented 100\% of the
validation sample's characters directly, with zero fallback of any kind.
This is a real, meaningful difference in what ``UNK rate = 0'' means
between the two languages' tokenizers.

\subsection{Vocab-size choice}

\textbf{Hindi: 8{,}000}, chosen on a fertility/embedding-budget trade-off.
The fertility gain from 8k$\to$10k (2.7\% relative) is much smaller than
5k$\to$8k (6.7\% relative), for meaningfully more embedding cost. Measured
directly: 8{,}000 produces more total tokens than 10{,}000 for Hindi
(505{,}852{,}028 vs.\ 491{,}883{,}387), pushing Hindi to 101.2\% of target
versus 10{,}000's 98.4\%.

\textbf{Hindi:} 505{,}852{,}028 total tokens (train 485{,}280{,}741 +
validation 10{,}484{,}640 + test 10{,}086{,}647) -- \textbf{101.2\% of
the $\sim$500M target}. Manual share: \textbf{28.65\% char-weighted},

share: \textbf{26.41\% token-weighted} (Nepali's pipeline never tracked

the pipeline's own absolute lane targets are also cleared independently:
manual 167{,}787{,}251 $\geq$ 100{,}000{,}000; downloaded 467{,}417{,}082
$\geq$ 400{,}000{,}000.

\textbf{Nepali was not always the plan.} This project's original Model L
was \textbf{Bhojpuri}: fully built, cleaned, split, tokenized, and
passing every validation check, with a documented, spec-permitted

available public data is genuinely much smaller than Nepali's.

of its absolute target and re-ran the full pipeline until both targets
were met, landing at 127.0\% of the planning target rather than a
documented shortfall.

\section{Limitations and What I Would Do Differently}
\label{sec:limitations}
% =====================================================================

\textbf{Hindi:}
\begin{itemize}
\item \textbf{The language-ID proxy is a real, acknowledged weak point},
though now largely historical since Bhojpuri is no longer this project's
Model L. \texttt{langdetect} has no Bhojpuri label, so
\texttt{likely\_bhojpuri} is a coarse lexical-marker filter, not a
trained classifier. This filter still runs unconditionally as part of
Hindi's own cleaning, even though its original purpose no longer applies
day to day.
\item \textbf{SentencePiece training samples the corpus} (22.0\% of
train characters). Standard practice; does not bias the held-out
evaluation numbers.
\item \textbf{Near-duplicate detection beyond exact-hash matching was cut
for time on Hindi's pipeline specifically.} Nepali's pipeline, by
contrast, does run MinHash/LSH -- now an asymmetry between the two
languages, not a shared gap.
\item \textbf{The BPE-vs-Unigram argument for Hindi is structural, not
empirically confirmed for Hindi specifically.} Nepali's pipeline, by
contrast, runs this comparison automatically -- it just never triggered.
\item \textbf{A small raw-total discrepancy} (528 characters, 0.00003\%)
was not root-caused. Too small to affect any pass/fail check.
\end{itemize}

\textbf{Nepali:}
\begin{itemize}
\item \textbf{Manual share is token-weighted, not char-weighted}, unlike
Hindi's -- Nepali's pipeline never added per-lane character tracking.
\item \textbf{Manual-lane concentration}: 91.6\% of manual tokens come
from one source (\texttt{news\_onlinekhabar}).
\item \textbf{SentencePiece's sampled-character count was not logged} by
Nepali's pipeline the way Hindi's was.
\item \textbf{The Nepali pipeline ran on a separate machine}; its
per-stage console logs for S08--S14 were not captured live, only
reconstructed from output artifacts in \texttt{log.md}.
\item \textbf{Cross-language check covers Nepali vs.\ Hindi only}
(Section~\ref{sec:crosslang}), not Nepali vs.\ Bhojpuri, since Bhojpuri is
not part of the final submission.
\end{itemize}
